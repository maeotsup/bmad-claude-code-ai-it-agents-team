# Rule Definition Schema

Rules are always-active guidelines that Claude follows when working in the project.
They are loaded from `.claude/rules/` and apply automatically to all agents and commands.

## Rule Types

| Type | File Pattern | Scope | Generated By |
|------|-------------|-------|--------------|
| **Safety** | `safety.md` | Universal — applies to every project | Copied from blueprint with minimal customization |
| **Language** | `{language}.md` | Per programming language | Generated based on detected/selected stack |
| **Framework** | `{framework}.md` | Per framework | Generated based on detected/selected stack |
| **Testing** | `testing.md` | Per test framework | Generated based on detected/selected stack |

## File Naming

- File name: `{topic}.md` (lowercase — e.g., `safety.md`, `python.md`, `react.md`)
- One rule file per concern
- Located in `.claude/rules/`

## Structure

Rules do not use YAML frontmatter. They use markdown headers and bullet lists.

### 1. Title (required, 1 line)

```markdown
# {Topic} Conventions
```

For safety rules: `# Safety Guardrails`

### 2. Sections (required, 2-6 sections)

Each section groups related rules under a `##` header.

```markdown
## Section Name
- {rule statement}
- {rule statement}
- **{keyword}**: {rule with emphasis on the key concept}
```

**Rules for sections**:
- 2-6 sections per file
- Each section has 3-8 bullet points
- Rules must be actionable — state what to DO or NOT DO
- Use bold for keywords that convey the core constraint
- SAFETY rules: every item starts with "Never" or "Always"
- LANGUAGE rules: organized by concern (style, database, error handling, imports)
- FRAMEWORK rules: organized by component (routes, templates, state management)
- TESTING rules: organized by concern (structure, coverage, patterns)

### 3. Separation of Universal vs. Project-Specific

**Critical for the generator**: Within each rule file, clearly separate:

- **Universal rules**: Apply to any project using this language/framework
  - Example: "Never use string concatenation in SQL queries"
- **Project-specific rules**: Only apply to this specific project
  - Example: "All UI strings must be in Estonian"

The golden examples contain ONLY universal rules. The generator adds project-specific
rules based on detection/interview results.

## Constraints on the Overall File

| Constraint | Value |
|------------|-------|
| Target length | 25–60 lines |
| Hard maximum | 80 lines |
| Hardcoded project references | NONE in golden examples |
| Emojis | NONE |
| Rule format | Actionable statements: DO this, NEVER do that |

## Safety Rules — Special Requirements

The `safety.md` file is semi-universal. It has two sections:

1. **Universal Forbidden Actions** — same for every project:
   - Never push directly to main/master
   - Never force push
   - Never run destructive git commands without explicit instruction
   - Never hardcode secrets
   - Never commit sensitive files

2. **Project-Specific Forbidden Actions** — added by the generator:
   - Project-specific dangerous commands (e.g., "Never run pipeline.py directly")
   - Project-specific protected files (e.g., "Never commit *.db files")

## Validation Checklist

- [ ] Title follows the `# {Topic} Conventions` pattern (or `# Safety Guardrails`)
- [ ] 2-6 sections with `##` headers
- [ ] Each section has 3-8 actionable bullet points
- [ ] No project-specific references in golden examples
- [ ] Safety rules use "Never" / "Always" phrasing
- [ ] Language/framework rules are organized by concern, not randomly listed
- [ ] Total line count within 25–80 range
